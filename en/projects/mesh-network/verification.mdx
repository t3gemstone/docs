---
title: "Verification"
description: "Verify direct IBSS links and multi-hop BATMAN-adv forwarding on T3 Gemstone O1"
---

This section verifies that the configured network is actually forwarding traffic across multiple wireless hops.

The mesh itself is not limited to three nodes. The procedure below uses **three T3 Gemstone O1 boards as the tested verification topology**.

The verification separates two different behaviors:

- Direct communication over the IBSS links
- Multi-hop communication over the BATMAN-adv mesh

This distinction is important because a successful end-to-end ping alone does not show whether the destination was reached directly or through an intermediate mesh node.

## 1. Test Topology

The tested physical topology was:

```text
Node 1 <------> Node 2 <------> Node 3

Node 1 <---------- X ----------> Node 3
```

During the test:

- Node 1 could communicate directly with Node 2.
- Node 2 could communicate directly with Node 3.
- Direct wireless reachability between Node 1 and Node 3 was not observed.

The direct-link subnet and mesh subnet were kept separate:

```text
wlan0 / IBSS: 192.168.100.N/24
bat0 / Mesh:   192.168.200.N/24
```

This makes it possible to compare direct IBSS reachability with BATMAN-adv mesh reachability.

## 2. Verify Direct IBSS Reachability

Before evaluating BATMAN-adv, verify the direct IBSS topology using the `192.168.100.x` addresses.

The IBSS configuration from the Setup section must already be active on all three nodes.

### Node 1

Test Node 2:

```bash
ping -c 5 192.168.100.2
```

Observed result:

```text
Success
```

Test Node 3:

```bash
ping -c 5 192.168.100.3
```

Observed result:

```text
Failure
```

### Node 3

Test Node 2:

```bash
ping -c 5 192.168.100.2
```

Observed result:

```text
Success
```

Test Node 1:

```bash
ping -c 5 192.168.100.1
```

Observed result:

```text
Failure
```

These results show the direct IBSS reachability observed during the test:

```text
Node 1 <------> Node 2 <------> Node 3

Node 1 <---------- X ----------> Node 3
```

IBSS provided the direct wireless links, but the two edge nodes were not directly reachable from each other in the tested physical topology.

## 3. Verify BATMAN-adv Neighbors

Complete the BATMAN-adv configuration from the Setup section on all three nodes.

Allow the mesh state to converge:

```bash
sleep 15
```

On Node 1:

```bash
sudo batctl n
```

In the test, Node 1 showed Node 2 as its direct BATMAN-adv neighbor.

On Node 2:

```bash
sudo batctl n
```

In the test, Node 2 showed both edge nodes as direct neighbors.

On Node 3:

```bash
sudo batctl n
```

In the test, Node 3 showed Node 2 as its direct neighbor.

The observed neighbor topology was therefore:

```text
Node 1 <------> Node 2 <------> Node 3
```

## 4. Verify the Forwarding Path

Inspect the originator table on Node 1:

```bash
sudo batctl o
```

In the test, Node 3 appeared as a known originator and Node 2 was selected as the next hop toward it.

Conceptually:

```text
Destination: Node 3
Next hop:    Node 2
```

Repeat the check on Node 3:

```bash
sudo batctl o
```

Node 2 should be selected as the next hop toward Node 1.

This information shows that BATMAN-adv learned a path to the remote edge node through the intermediate node.

## 5. Trace the Multi-hop Path

From Node 1, trace the BATMAN-adv path toward Node 3 using its originator MAC address:

```bash
sudo batctl tr <NODE3_MAC>
```

The observed path should include Node 2 before Node 3:

```text
Node 2
Node 3
```

You can also test connectivity directly at the BATMAN-adv layer:

```bash
sudo batctl ping <NODE3_MAC>
```

These commands inspect the mesh path independently of the IP-level ping test.

## 6. Test End-to-End Mesh Traffic

With BATMAN-adv active, test communication using the `bat0` addresses.

From Node 1:

```bash
ping -c 5 192.168.200.3
```

Observed result:

```text
Success
```

From Node 3:

```bash
ping -c 5 192.168.200.1
```

Observed result:

```text
Success
```

The direct IBSS test and the mesh test can now be compared:

```text
Direct IBSS:

Node 1 ---------------- X ----------------> Node 3


BATMAN-adv:

Node 1 ------------> Node 2 ------------> Node 3
```

Node 1 and Node 3 were not directly reachable over the tested IBSS topology, while communication between their `bat0` addresses succeeded after BATMAN-adv was enabled.

Together with the `batctl n` and `batctl o` results, this verifies that the edge-node traffic was forwarded through Node 2.

## 7. Result

The three-node test produced the following verification chain:

1. Node 1 could directly reach Node 2 over IBSS.
2. Node 3 could directly reach Node 2 over IBSS.
3. Direct IBSS reachability between Node 1 and Node 3 was not observed in the tested physical topology.
4. `batctl n` showed the expected direct-neighbor relationships.
5. `batctl o` showed Node 2 as the next hop toward the remote edge node.
6. `batctl tr` showed the intermediate mesh hop.
7. Communication between the edge-node `bat0` addresses succeeded.

The verified forwarding path was:

```text
Node 1 ------> Node 2 ------> Node 3
```

and in the reverse direction:

```text
Node 3 ------> Node 2 ------> Node 1
```

This verifies Layer 2 multi-hop forwarding with BATMAN-adv over the underlying IBSS wireless links in the tested T3 Gemstone O1 topology.
